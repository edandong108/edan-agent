# 需求整理 · 任务运维（队列状态 / 队列分析）

> 提炼自 `方案/离线作业队列状态查询-评审一页纸.html`（2026-09-09 评审通过，状态：已实现）。
> 原始需求：业务方《离线作业SLA保障方案——第一阶段 V2》PDF，原件留 `核心文档/SLA功能/需求/`（二进制不入仓，本仓记路径）。

## 业务痛点（一页纸 §一）

- 积压不可见：离线作业经队列提交后，运维只能去执行日志逐条翻，看不出"此刻排了几个、等多久"
- 僵尸无感知：心跳停摆的死实例混在 RUNNING 里，占并发额度却不产出
- SLA 不可量化："超基线 30min 的占比"靠人工数日志，高优/普通达标率无口径、无趋势
- 事后难复盘：某天出问题，无法回看"14:30 那波积压是谁、入口暴增还是出口堵"

## 需求条目与验收标准

| 编号 | 需求 | 验收标准 |
|------|------|---------|
| R1 | 当前/历史时刻队列快照：排队/运行/僵尸三态计数 + 明细 | `GET /portal/queue-status/snapshot` 返回三态计数与明细；历史回看精度到分钟；当前态 10s 可刷新（默认关） |
| R2 | 按天队列分析：5min 切片（288 点）后端聚合 | `/portal/queue-analysis/analyze` 返回 5 KPI + 切片序列 + 按小时表 + Top10（可分页） |
| R3 | SLA 达标率口径：基线一期固定 30min，高优目标 100%、普通 ≥95% | 分析页 KPI 卡展示两档达标率与超基线数；P90 > 30min 即破防 |
| R4 | 僵尸检出：心跳停摆超阈值（heartbeat×20=600s） | 快照页与分析页展示僵尸数（取当日峰值）；只展示，不联动任何动作 |
| R5 | 高优/普通优先级展示（`sla_priority`） | 明细列展示；一期仅展示不参与排序，排队恒按 `submit_time` FIFO |

## 范围外（一期明确不做，一页纸 §四）

- 不改调度逻辑、不改 entry.py 提交与出队、不参与排队、不写库（只读）
- 不做自动告警推送、自动重跑/杀僵尸、导出、跨天对比
- SLA 基线固定 30min（后续可演进为按表配置，原始方案即每表设基线）
- 仅统计经队列提交的作业（直启作业不在快照中）

## 数据与权限口径

- 数据来源：已有 `schedule_queue`（append-only）+ `job_instance` + `job`（取湖表名），**无新建表**（MySQL 表改造由底层开发完成）
- 权限：只配 IAM 菜单，不配权限码（只读，能进数据交换即可）
- 无新增中间件；Nacos 3 个配置项与执行端 entry.py 侧同名（`etl.schedule.*`）
